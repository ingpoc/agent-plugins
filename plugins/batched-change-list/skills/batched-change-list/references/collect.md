# Collect

Run `bcl start` to record Collect. After a rollover, only this first `bcl start` begins Collect on the new list and points its viewer to that list; rollover itself keeps the old viewer in place. Carried findings that were `in_progress` start as `untested` so the page says work is underway only after it starts on this list. Identify the product, installed build or revision, test scope, reference or expected behavior, and what the user has authorized. Preserve existing work, user priorities, authorizations, issue IDs, evidence, and verification history. Test the real artifact using the appropriate project and platform tools.

Record each finding once with an ID, affected state, expected and actual behavior, severity, status, and concrete evidence. Attach screenshots, logs, reproduction steps, or links when available. Mark missing evidence, uncertainty, and untested paths explicitly; observability events are supporting evidence, not proof of cause. Keep unrelated work separate.

Add feedback as it arrives without starting a fix for every item. If the user is actively testing, give a short ready-to-run test card with the exact prompt or actions, expected result, and what to report back. Record the app/build and a timestamp or run/session reference when available; attribute telemetry to that test only when evidence links them, otherwise label it as an unlinked lead. Fix urgent security, data-loss, or blocking issues promptly; do not delay explicitly requested work for batching.

For a message during work, answer a question or status request briefly and continue; treat a correction as steering unless it explicitly cancels or replaces the task. Add or update the finding and acceptance criteria before the related fix. Preserve earlier evidence, distinguish reported behavior from verified results, and mark dependent plans and checks for rework when their inputs change. Do not infer the tested version from the current installation or report an unanswered prompt as a decision.

Collect what the agent can verify itself before asking the user to test. For the project's observability findings, run `python3 "$SKILL_DIR/scripts/collect_observability.py" --project-id <project-id> [--project-dir <path>]`. The helper checks snapshot freshness, runs the developer-observability collector only when stale, and verifies that a fresh snapshot covers the requested project directory by its full path before reading diagnosis and the project's issue list. A matching basename is not enough, and a coverage key whose status is `missing` does not count as coverage. An insufficiently covered fresh snapshot is reported as an error; it is not silently reused or recollected. For each relevant result, use its `finding_key` as the stable ID and `evidence_path` as supporting evidence when adding with `bcl add` or appending with `--into`. Group related telemetry leads with stable IDs and provenance; link evidence to an existing issue where it describes the same problem, and keep unlinked leads explicitly unconfirmed. Do not count records as separate bugs. Before a build or install, identify the required PR, release gate, installed path, and acceptance checks so one authorized cycle covers the batch.

Write `summary`, `impact`, and `done_when` in plain words for a non-technical reader. Put commands, SHAs, counts, timestamps, and log quotes in `observed` or `details`. Collect stays open; findings added at any time join the next Plan & fix. After Collect, move to [Present](present.md).
