# Verify

Run `bcl verify` only after Install has been reached in the current cycle. Verify each installed group (or wave) as soon as its build is in place; do not wait for other lanes. Use `bcl verify --ids …` for that group or wave. Live verify is serialized (one Mini, island, and Comet) and must run the `verify.command` stored on the group at Plan, not an improvised substitute. Finding-status writes and `bcl verify` update each plan group's `verify` state to `pending`, `verified`, `failed`, or `partial`, with `fixed`, `failed`, and `total` counts. Mark `verified_fixed` as evidence lands; the gate counts those fixes immediately.

Use `Verified fixed` only after the acceptance criteria pass the relevant tests and validation, plus installed/live verification when the issue affects runtime. The agent performs available live checks and records evidence itself; request user testing only for a genuinely inaccessible or subjective check. If user confirmation is required, give exact actions and expected result, and retain `Awaiting user test` until confirmed. Link observability and independent readback when applicable; an absence of events, source tests, or a green aggregate snapshot alone does not prove a fix. If proof is missing or conflicts, use `Untested`, `Awaiting verification`, `Failing`, or `Blocked` as appropriate. Separate a failed release gate from confirmed product defects and retain failed runs and successful isolated retries. Before declaring a fix complete, see [prove it works](principles.md#prove-it-works).

Collect observability once before the relevant live batch and once afterward, using the same session and build identity where available. Treat older or unlinked telemetry as a lead. After each coherent test or verification batch, update the authoritative findings and regenerate the view; reconcile per-item status, navigation badges, counts, build/head and evidence together.

## Installed verification runs

After each PR install, start a distinct verification run with `{"action":"start-verification","run":{"id":"unique-install-id","build":"installed version","revision":"installed revision","installed_at":"ISO 8601 timestamp","install_evidence":"receipt or independent readback"}}`. Existing product statuses, including fixed, remain unchanged. Every issue starts as not checked for that installation; added issues join the active run as not checked. Use tracker batch commands for these writes; see [tracker.md](tracker.md).

Before checking an issue, write and render `{"action":"start-check","run_id":"…","id":"ISSUE-01","observation":"what is visible before the check","observed_at":"ISO 8601 timestamp at or after installed_at"}`. Repeat it as a heartbeat with the observation time for that check. The manager rejects an explicit `"carried_over":true` or `"no_new_observation":true` marker and any check without an `observed_at` timestamp for this run. To recheck a finished issue on the same install, use the same `start-check` with `"recheck":true` and a fresh `observed_at`. When finished, write `{"action":"finish-check","run_id":"…","id":"ISSUE-01","outcome":"fixed|not_fixed|blocked|inconclusive","evidence":"proof or reason"}` in a separate invocation. `fixed` requires `verified_fixed` and verification references; a newly observed `not_fixed` result changes product status to failing. Blocked and inconclusive do not change a prior fixed status. Only `{"action":"complete-verification","run_id":"…"}` after every issue has a result or an explicit blocker; blocked/inconclusive are not counted as checked. If another install occurs first, start a new run with a new ID; the earlier run is retained as interrupted.

A completed current check can be corrected with `{"action":"correct-check","run_id":"…","id":"ISSUE-01","outcome":"not_fixed|blocked|inconclusive","reason":"specific evidence and reason for correction"}`. A correction to fixed still requires a new verification check and proof.

To show current plugin inventory separately from the verification run, set `tracking.installed_plugins` to `{"observed_at":"timestamp","source":"manifest or other provenance and limitations","versions":{"plugin-name":"version"}}`. Read installed identities before recording them; do not infer running versions from manifests.

For spoken tests, compare the bounded local transcript and tool events with the observed outcome; a user’s direct confirmation can establish the visible result. Keep transcripts private and distinguish claims from observations.
