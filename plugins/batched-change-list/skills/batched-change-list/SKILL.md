# Batched change list

> **Self-validate after edits.** Run `python3 -m unittest discover -s scripts -p 'test_*.py'` from this skill directory.

Use the existing findings JSON as the sole tracker; HTML is its rendered view. Preserve work, user priorities, authorizations, issue IDs, evidence, and verification history. Never infer acceptance from unlinked telemetry or source tests alone.

The page is the user's only view of progress. As each phase or issue group starts, use `set-activity` to set its stage, mark affected IDs `in_progress`, and write one timestamped `Now` line. Clear the stage with `set-stage` and `null` on pause or finish; do not repeat `Current step` details on findings. Use [tracker operations](references/tracker-operations.md) for exact commands and recovery.

When adding a finding, write `summary`, `impact`, and `done_when` in plain words for a non-technical reader. Put commands, SHAs, counts, timestamps, and log quotes in `observed` or `details`; the manager warns when a summary looks like log text or is missing.

Each list uses Collect and Present once, then loops through Plan & fix, Install, Verify, and (after a full cycle only) Introspect. Collect stays open for new findings; pick them up on the next Plan & fix. The strip shows `Round tracking.cycle`; each tracker starts at round 1 and a rollover advances it. The gate passes at 15 `verified_fixed` findings by default, configurable with `tracking.rollover_threshold`, or when no open findings remain. If it fails, return to Plan & fix; if it passes, report and roll over to a new list at Collect. Use the native plan tool for substantial batches when available.

1. **Collect** (`collect`). Identify product, build, scope and expected behavior; exercise accessible checks and record each finding once. Use `scripts/manage_findings.py` and load [tracker operations](references/tracker-operations.md) when reading or changing records. For feedback, screenshots, telemetry and user test cards, load [collection and reporting](references/collection-and-reporting.md).
2. **Present** (`present`). Render the list once with `scripts/render.py` or `batch --render`. For live details, `scripts/serve.py --data` discovers installs and refreshes IST timestamps on each request. See [collection and reporting](references/collection-and-reporting.md) for command options and the fixed-port viewer. Verify navigation and show concise evidence.
3. **Plan and fix** (`plan_fix`). Start only after the finding is logged and set in progress; the manager refuses `plan_fix`, `install`, or `verify` without an in-progress finding. Group issues by root cause and acceptance checks; use existing gates and minimal safe build/install cycles. The main agent owns planning, integration, tracker and final evidence review. Route each task to the cheapest model and effort that can do it; delegate bounded independent work with owned files and focused checks when beneficial, keep small/coupled work inline, and use one operator per shared surface. Load [fix and verify](references/fix-and-verify.md) for delegation and gate details, and follow its **Fast cycle**: triage once, fix independent groups in parallel, install once, run one combined live check per build.
4. **Install** (`install`). Update the authorized PR before installing its exact head when required.
5. **Verify** (`verify`). After each install, load [verification runs](references/verification-runs.md), start a distinct run, then start and finish each issue check so its card appears first while checking. Perform accessible checks before asking the user; use [fix and verify](references/fix-and-verify.md) for acceptance requirements.
6. **Introspect** (`introspect`). Only after a full cycle; small follow-up cycles skip it. Use [introspect](references/introspect.md) for one evidence-based pass and one `WF-` task.
7. **Gate** (`gate`). Read the step counter. If fewer than the configured threshold are `verified_fixed` and open findings remain, return to Plan & fix. The manager refuses `report_rollover` or `rollover` until the gate passes; `batch --force` records an override.
8. **Report and roll over** (`report_rollover`). Run `compact` before `audit` to remove carry-over checks, process/history details, old evidence, and archived findings while preserving active finding IDs and statuses. The audit rejects tracker JSON over 320 KiB and directs the agent to compact. Batch tracker changes, regenerate the HTML, and reconcile statuses, navigation and build identity. When work moves to a new PR, retain the authoritative JSON and its history, update its PR identity, and render a new PR-named HTML file; preserve the prior report and update current links. `verified_fixed` requires relevant tests plus installed/live acceptance when applicable; blocked or inconclusive is not proof. When the configured gate passes, finish accessible verification, commit and push the verified-fix report, and propose the merge with its evidence. Merge only under an explicit user instruction or an applicable standing policy in the product repository’s agent instructions; absent either, stop there and ask. After a merge, verify it, then fetch the authoritative remote and fast-forward the local `main` checkout without overwriting local changes before starting the follow-up PR. Open a follow-up PR if unresolved findings remain, preserving all records and history in the same tracker. Do not otherwise merge, publish, install, send messages or run intrusive tests without authorization.
